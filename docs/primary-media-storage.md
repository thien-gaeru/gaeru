# Primary file storage

Neon Object Storage (private assets bucket) is primary for product images, banners, article covers, product videos and chat documents/media. Production uploads require working storage and never fall back to inline database bytes. Development/tests can use inline fixtures unless NEON_STORAGE_UPLOADS_ENABLED=true. Explicit false in production rejects uploads.

The existing PostgreSQL database remains authoritative for accounts and encrypted settings, orders, payments, stock, warranty, article text, chat messages, ownership/permissions, filenames/MIME and file references. File bytes are not sent to the Chat AI by this change. Existing application assets and source code remain in the deployment package.

Object keys use fixed namespaces products/, banners/, news/, videos/ and chat/ with UUID names; no filenames, account IDs or customer names appear in keys. No public bucket ACL or direct storage URL is introduced. Existing app endpoints enforce authorization/publication before loading objects. Private files retain no-store, nosniff and forced download for documents; inline video range handling is preserved.

The bytea column retains a small GAERU_S3_V2 reference envelope (key, exact byte count and SHA-256). Reads validate object bytes. Legacy inline bytes and GAERU_S3_V1 image references remain readable. shopping_chat_files.byte_size separately tracks logical file sizes for quota and response metadata. Deploy db/primary-media-storage.sql through the normal migration runner before serving the new code. No core business table is moved.

Rollout: preserve recoverable media backups; upload each legacy object under a new immutable key; download and hash-check it; deploy/migrate and confirm X-GAERU-Media-Storage:2 on a published news image; then run scripts/activate-neon-media.cjs PRIVATE_MANIFEST.json without --apply to rehearse. Set DATABASE_URL and storage credentials in the operator environment, then use --apply only after verification. The manifest contains private media bytes and must stay out of Git. Activation compares source bytes/timestamps and retains IDs, MIME, timestamps, ownership and logical sizes. Backups support restoring exact prior bytea values. Never activate pointers before the compatible reader is deployed.

Storage upload followed by a failed/uncertain database transaction may leave an unreferenced object. It is deliberately retained to avoid deleting an object that a committed transaction may reference. Reconcile references against object inventory before any later cleanup; this rollout does not delete old objects, private records or backups. Object storage and database need separate backups/retention; a database restore alone does not restore missing objects. Existing account deletion still removes its database records; object cleanup requires reconciliation and is not made public by loss of a database reference.

Verification includes storage failure without database fallback, checksum failures, invalid keys, legacy compatibility, guest chat isolation, draft-image visibility, idempotent attachment submission, original logical quota, and video range responses. Live legacy content activation remains a separate gated operation after deployment.
