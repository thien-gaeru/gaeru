# Account security and owner recovery

Admin: open **Bảo mật tài khoản**. Owner and staff can change their password, bind a recovery email and phone, and select **Mã qua email** or **Ứng dụng xác thực**. Customer: open **Mật khẩu & xác thực hai yếu tố** on the account page. Customer contact changes continue using the separately verified profile flow.

Every account starts with MFA off; deployment does not enable it or alter any production credential. Enabling requires the current password, the existing factor when already enabled, and proof of the new method. Email must be verified before either MFA method can be enrolled. Authenticator enrollment uses a manual base32 setup key compatible with standard SHA1 TOTP, 6 digits and a 30-second period. Enrollment is not active until a valid application code is supplied. Switching methods or disabling also requires the current factor or a one-time backup code.

Eight random 64-bit backup codes are displayed once on enrollment. Store them securely; the database retains only SHA-256 hashes. Regenerating the factor invalidates the old codes. Setup keys are encrypted with AES-256-GCM, using `AUTH_ENCRYPTION_KEY` when present, otherwise the existing `SESSION_SECRET`. Back up this key separately from the database; changing it prevents decryption of existing authenticator secrets. Backup codes remain usable for recovery of a lost authenticator. No keys are sent to an external QR service.

Email codes expire after five minutes and allow at most five attempts per challenge. Setup sessions expire after five minutes. Password confirmation creates only a pending login when MFA is enabled; protected routes stay inaccessible until the second step. Authenticator counters are consumed transactionally to reject replay, including reuse of the enrollment code. Recovery codes are also consumed under the account lock. Login/API rate limits and CSRF apply. Security responses are not cached; sensitive plaintext is not persisted in browser storage or audit events.

Owner password changes persist as a bcrypt hash in `account_security`, overriding the bootstrap environment password after the first change. The environment username still names the owner. Environment credentials remain the initial fallback only while no owner password override exists. Changing the password or security settings rotates the current session and revokes older sessions; staff password changes increment the existing staff authorization version. Customer password reset also revokes prior account sessions while retaining MFA.

Bind the owner's email and phone before relying on recovery. Binding requires a code from the proposed email (plus the existing factor when enabled); the phone is authorized by email, not SMS. **Quên tài khoản hoặc mật khẩu?** sends the admin username and a one-time, 30-minute reset link when the email and phone match a verified admin contact. Reset additionally requires the active factor or a backup code when MFA is enabled. An email-factor account can request its factor code from the reset page. Reset does not disable MFA. No administrative recovery is available before contacts are configured.

Migration `account-security.sql` is additive and runs before serving requests. Existing owner sessions remain valid until an explicit security change. PostgreSQL stores the settings and challenge state. Security changes are recorded without passwords, seeds or codes. Test-only mailers and embedded PostgreSQL exercise owner recovery/password override, both factors, staff/customer enforcement, replay and session revocation. RFC 6238 SHA1 vectors validate the TOTP implementation. Live SMTP delivery and browser visual behavior require separate verification; tests never enroll a production account.
